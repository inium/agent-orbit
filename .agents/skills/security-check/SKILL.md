# Security Check

## 범위와 실행 원칙

- 지정된 파일·커밋·변경 범위를 우선한다. 범위가 없으면 현재 프로젝트 전체의 코드와 설정을 점검한다. `src/`, `web/`, Dockerfile·Compose·셸 스크립트, 의존성·잠금 파일, 개발 도구 설정과 관련 문서를 포함한다.
- git-commit 스킬에서 호출하면 코드 리뷰 전에 스테이징 범위만 점검한다. 문서·포맷 변경도 민감정보는 확인하고, 위험한 코드·의존성·deprecated 검사는 실제 변경과 관련된 부분에 적용한다. 수정 후 스테이징 및 커밋 진행 여부는 호출한 git-commit 스킬을 따른다.
- 파일 목록과 Git 상태를 먼저 확인한다. 스테이징 검사에서는 인덱스 내용(`git show :경로`)을 기준으로 읽고 미스테이징 변경과 구분한다. 기본적으로 의존성 설치 디렉터리·캐시·바이너리는 제외한다. Git 이력 검사는 요청된 경우에 수행하고, 현재 파일 검사만으로 과거 노출까지 없다고 단정하지 않는다.
- 점검은 읽기 전용으로 수행한다. 자동 수정·포맷·의존성 설치 및 업데이트·키 폐기·Git 이력 재작성·커밋·push는 자동 실행하지 않는다. 실제 자격증명으로 외부 서비스를 호출하거나 공격 코드를 실행해 유효성·악용 가능성을 시험하지 않는다.

## 민감정보 검사

- 하드코딩된 비밀번호, API 키, 액세스·리프레시 토큰, 개인키, 인증정보가 포함된 연결 문자열·URL, 쿠키·세션 비밀키를 찾는다. 소스뿐 아니라 예제 설정, 테스트 자료, 스크립트, 문서, 잠금 파일의 사설 레지스트리 인증정보와 프런트엔드로 전달되는 값도 확인한다.
- `.gitignore`와 추적 파일 목록으로 `.env`, 인증 파일 및 백업 파일이 커밋되는지 확인한다. 무시된 `.env`에 자격증명이 존재하는 것 자체는 코드 노출로 분류하지 않는다. 필요할 때 키 이름과 사용 경로만 확인하고, 환경 파일 전체를 출력하지 않는다.
- 검색은 먼저 `rg -l` 등 파일명만 반환하는 방식으로 후보를 좁힌다. 후보 내용은 값이 출력되지 않도록 마스킹한 도구로 확인한다. 원문 비밀을 포함할 수 있는 `cat`, 일반 `rg -n`, diff, 로그 또는 스캐너 출력을 그대로 도구 결과에 노출하지 않는다. 외부 검색·보고서·임시 파일에도 비밀 값을 전달하지 않는다.
- 스캐너가 있으면 redaction 옵션과 검사 범위를 확인한 뒤 사용한다. 없으면 로컬 검색과 데이터 흐름 추적으로 진행하고 탐지 한계를 밝힌다. 값 형식·대입·사용 맥락을 확인하여 플레이스홀더, 공개 식별자, 환경 변수 참조와 실제 비밀 후보를 구분한다. 실제 키인지 확인하기 위해 API를 호출하지 않는다.
- 보고에는 파일·줄, 정보 종류, 노출 경로만 적고 값은 `[REDACTED]`로 표시한다. 실제 키 노출이 의심되면 코드에서 제거하는 것과 별개로 소유자에게 폐기·재발급 및 이력·배포물 확인 필요성을 설명한다.

## 위험한 코드와 설정

| 영역         | 확인 사항                                                                                                                                                                             |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Python·API   | 입력에서 SQL·명령·경로로 이어지는 주입, `shell=True`·`eval`·`exec`, 신뢰할 수 없는 pickle·YAML 역직렬화, SSRF·경로 탈출, 인증·권한 및 스레드별 데이터 격리, 오류·로그의 민감정보 노출 |
| 에이전트·RAG | 문서·모델 출력을 도구 인자나 실행 코드로 신뢰하는 경로, 프롬프트 주입으로 인한 권한 확대·정보 유출, 도구 접근 범위, 사용자 간 검색·대화 데이터 노출, 무제한 반복·입력·외부 호출       |
| web          | 신뢰할 수 없는 값의 `innerHTML`·HTML 렌더링·URL 삽입, 브라우저 번들의 비밀, 토큰·대화 저장, 외부 스크립트와 API 요청의 신뢰 경계                                                      |
| Docker·운영  | 빌드 인자·레이어·이미지의 비밀, 과도한 권한·Docker 소켓·호스트 마운트, DB 외부 노출, TLS 검증 해제, CORS와 실제 인증 구성, 데이터 삭제·위험한 셸 확장                                 |

- 위험한 함수의 존재만으로 취약점으로 확정하지 않는다. 입력 출처, 검증, 권한 경계, 실행 경로와 실제 피해 조건을 추적한다. 로컬 개발 전용 설정과 외부 배포 시 위험을 구분한다.

## 의존성·Deprecated 검사

- `pyproject.toml`·`uv.lock`, `package.json`·`package-lock.json`, Docker 이미지와 코드의 사용 API를 확인한다. 선언 범위와 잠금 파일의 실제 버전을 구분한다.
- 취약점과 deprecated·제거 예정·지원 종료 여부는 유지관리자의 공식 문서·변경 이력·보안 공지 또는 공식 취약점 데이터베이스로 현재 상태를 확인하고 링크와 확인 날짜를 보고한다. 비밀·비공개 코드는 외부 조회에 보내지 않는다.
- 기존 감사 도구를 사용할 수 있으면 읽기 전용 모드로 실행한다. 의존성 목록이 외부 서비스로 전송되는 감사는 전송 범위를 알리고 승인받는다. `audit fix`나 자동 업그레이드는 실행하지 않는다.
- deprecated는 곧 취약점을 뜻하지 않는다. 보안 취약점, 지원 종료, API 사용 중단 권고를 구분하고 실제 사용 버전·호출부, 영향 조건 및 대체 방법을 제시한다. 최신 버전이 아니라는 이유만으로 문제로 분류하지 않는다. 최신 공지를 확인할 수 없으면 미확인으로 표시하고 취약점이 없다고 결론 내리지 않는다.

## 보고와 수정

1. 항목마다 식별자(`S1` 등), 심각도, 확인된 문제인지 의심인지, 파일·줄 링크, 발생 조건·영향, 마스킹된 근거, 권장 수정과 검증 방법을 적는다. 심각도는 영향과 악용 조건에 따라 치명적·높음·보통·낮음으로 구분한다.
2. 중요한 문제부터 보고하고 검사 범위·도구·검증하지 못한 부분을 명시한다. 문제가 발견되지 않아도 점검 범위 안에서 탐지하지 못했다는 의미로 설명한다.
3. 수정 사항이 있으면 구체적인 수정안을 제시하고 `S1, S2를 제안한 방식으로 수정할까요?`처럼 승인받은 뒤 적용한다. 이 스킬의 “수정은 사용자 승인 후 진행” 규칙을 링크와 함께 밝혀 확인 이유를 설명한다. 이미 구체적인 수정안에 승인받았다면 다시 묻지 않는다.
4. 승인된 항목만 수정하고 관련 검증을 실행한다. 추가 수정이 필요하면 별도로 보고하고 승인받는다. 결과에 해결한 항목과 남은 위험을 알린다. 키 폐기, 외부 설정 변경, Git 이력 재작성 및 커밋·push는 각각 요청된 범위에서만 진행한다.
