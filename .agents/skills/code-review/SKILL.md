# Code Review

## 범위와 진행 원칙

- 사용자가 지정한 파일, 변경 사항 또는 커밋을 우선 검토한다. 범위를 지정하지 않으면 현재 작업 트리의 스테이징·미스테이징 변경과 새 파일을 검토한다. 변경이 없으면 프로젝트 전체를 검토한다.
- git-commit 스킬의 커밋 전 리뷰에서는 스테이징 변경만 검토한다. 부분 스테이징 파일은 인덱스 내용(`git show :경로`)을 기준으로 읽고, 관련 코드는 영향 확인용으로만 참조한다. 커밋 진행 여부와 수정 후 스테이징은 호출한 git-commit 스킬의 절차를 따른다.
- `git status --short`, `git diff`, `git diff --cached`로 작업 상태를 확인하고, 대상 코드의 호출부와 설정을 함께 읽어 실제 영향을 추적한다. 전체 리뷰는 아래 영역을 살피되, 변경 리뷰는 영향을 받는 관련 영역으로 확장한다.
- 리뷰 단계에서는 파일 수정, 자동 포맷, 의존성 설치, 스테이징 및 커밋을 하지 않는다. 사용자 작업을 보존하고 비밀 값은 보고서에 노출하지 않는다.
- 읽기 전용 검사와 기존 테스트로 근거를 확인한다. API 서버 초기화·에이전트 호출은 외부 모델 호출이나 DB 접근을 유발할 수 있으므로, 부작용을 확인한 뒤 필요한 실행 범위를 별도로 설명하고 승인받는다. 컨테이너 재시작, DB 데이터 변경 및 볼륨 삭제도 리뷰만을 위해 실행하지 않는다.

## 발견 사항 보고와 수정 승인

1. 실제 오류, 회귀, 데이터 손실, 보안 문제, 의미 있는 성능·사용성 문제를 우선한다. 취향에 따른 리팩터링이나 포맷 차이는 필수 수정으로 제시하지 않는다.
2. 발견 사항마다 식별자(`R1` 등), 우선순위, 파일·줄 링크, 발생 조건, 영향과 근거, 구체적인 수정안 및 검증 방법을 적는다. 확인된 문제와 확인이 필요한 추정을 구분한다. 동일 원인의 문제는 묶는다.
3. 우선순위는 P0(즉각 대응이 필요한 치명적 문제), P1(높은 영향으로 우선 수정), P2(일반 수정), P3(낮은 영향의 개선)로 표시한다. 문제 수를 채우기 위해 근거가 약한 항목을 만들지 않는다.
4. 중요한 발견 사항부터 보고하고, 검토 범위와 실행한 검사·미검증 사항을 짧게 덧붙인다. 발견한 문제가 없으면 그대로 알리고 검증 한계를 명시한다.
5. 수정할 사항이 있으면 보고 후 `R1, R2를 제안한 방식으로 수정할까요?`처럼 대상과 방법이 드러나는 질문으로 수정 여부를 확인하고 기다린다. 이는 이 스킬의 필수 절차이며, 보고서에 이 스킬의 링크와 “사용자의 수정 승인을 받은 뒤 적용한다”는 규칙을 간단히 밝혀 승인 요청 이유를 설명한다. 리뷰 요청 자체를 수정 승인으로 해석하지 않는다.
6. 사용자가 승인한 항목과 방법만 수정하고 관련 검증을 실행한다. 이미 보고한 구체적인 수정안에 대한 승인이 있으면 재확인하지 않는다. 새 문제나 범위 확대가 필요하면 먼저 보고하고 추가 승인을 받는다. 승인이 없거나 리뷰만 원하면 보고로 마친다.
7. 수정 후 반영한 항목, 검증 결과, 남은 문제를 알린다. 커밋·push는 별도 요청이 있을 때만 진행한다.
