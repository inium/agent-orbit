# Git Commit

## 호출 기본 동작

- 추가 지시 없이 `$git-commit`만 호출하면 현재 스테이징된 변경 전체를 커밋하라는 요청으로 처리한다. 사용 목적이나 커밋 진행 여부를 다시 묻지 않고 아래 보안 점검·리뷰·검증 절차를 수행한다.
- 이 경우 커밋 대상은 호출 시점의 인덱스 내용이다. 미스테이징 변경과 미추적 파일은 자동으로 추가하지 않으며, 부분 스테이징 파일도 인덱스 내용만 포함한다.
- 스테이징된 변경이 없으면 커밋할 변경이 없다고 알리고 종료한다. 다른 변경을 자동으로 스테이징하거나 빈 커밋을 생성하지 않는다.
- 추가 지시가 있으면 해당 요청을 우선한다. 메시지 작성 요청이나 스킬 자체의 수정 요청을 커밋 실행으로 해석하지 않는다.

## 메시지 규칙

```text
type(scope): gitmoji 한글 설명
```

- 타입은 아래 표의 영문 소문자를 사용한다. scope는 모든 커밋 메시지에 반드시 하나를 지정한다.
- scope 허용 목록은 프로젝트 루트의 `.vscode/settings.json`에 있는 `conventionalCommits.scopes`를 기준으로 한다. 메시지를 작성하기 전에 해당 항목을 읽고 목록 안에서 선택한다. 목록에 없는 scope를 임의로 만들거나 설정 파일을 자동으로 수정하지 않는다. 설정이 없거나 목록이 비어 있으면 사용자에게 확인한다.
- gitmoji는 콜론 뒤 설명의 첫 문자로 실제 이모지 한 개를 사용한다. 타입 앞에 넣거나 `:sparkles:` 같은 코드를 쓰지 않는다.
- 제목 설명과 선택적인 본문은 한글로 작성한다. 코드 식별자, 제품명, 패키지명은 원문을 유지해도 된다.
- 제목은 변경 결과를 간결하게 설명하고 끝에 마침표를 붙이지 않는다. 기존 commitlint의 길이 제한을 따른다.
- 본문이 필요하면 제목 뒤에 빈 줄을 두고 변경 이유와 영향을 한글로 적는다.
- 호환성을 깨는 변경은 `type(scope)!: gitmoji 한글 설명`으로 표시하고, 필요하면 `BREAKING CHANGE: 한글 설명` 푸터를 추가한다.

| 타입     | gitmoji | 용도                           |
| -------- | ------- | ------------------------------ |
| feat     | ✨      | 기능 추가                      |
| fix      | 🐛      | 버그 수정                      |
| docs     | 📝      | 문서 수정                      |
| style    | 🎨      | 포맷 및 코드 스타일 변경       |
| refactor | ♻️      | 동작을 유지하는 코드 구조 개선 |
| perf     | ⚡️      | 성능 개선                      |
| test     | ✅      | 테스트 추가 및 수정            |
| build    | 📦️      | 빌드 시스템 및 의존성 변경     |
| ci       | 👷      | CI 설정 변경                   |
| chore    | 🔧      | 기타 설정 및 유지보수          |
| revert   | ⏪️      | 기존 변경 되돌리기             |

```text
feat(web): ✨ 에이전트 상태 대시보드 추가
fix(api): 🐛 연결 종료 시 상태 갱신 오류 수정
docs(docs): 📝 프로젝트 실행 방법 정리
chore(tooling): 🔧 커밋 검사 설정 추가
```

## Scope 선택 기준

허용 목록은 설정 파일에서 읽고, 아래 기준으로 변경의 주된 목적에 맞는 scope를 선택한다.

| scope     | 적용 범위                                                |
| --------- | -------------------------------------------------------- |
| `web`     | `web/`의 화면, JavaScript, CSS, 정적 자산                |
| `api`     | `src/app/main.py`의 요청·응답, SSE, 오류 처리            |
| `agent`   | 에이전트 구성, 도구 연결, 모델 설정 및 백엔드 공통 로직  |
| `rag`     | 문서 분할·적재·검색, 벡터 저장소, retriever              |
| `prompts` | 프롬프트 템플릿과 로더                                   |
| `data`    | `data/`의 검색 원본 규정·매뉴얼                          |
| `infra`   | Dockerfile, Compose, 실행·종료 스크립트, 환경 변수 예시  |
| `tooling` | Prettier, Husky, commitlint, 커밋 스킬 및 개발 도구 설정 |
| `docs`    | README, AGENTS.md 등 프로젝트 안내 문서                  |
| `repo`    | 특정 영역으로 한정할 수 없는 프로젝트 전체 변경          |

- 프롬프트와 에이전트 코드를 함께 바꿔 에이전트 동작을 개선하면 `agent`, 프롬프트만 수정하면 `prompts`를 사용한다.
- 의존성 변경은 해당 의존성의 사용 목적에 맞는 scope를 선택한다.
- 독립적인 변경은 커밋을 나눈다. 여러 영역을 함께 수정해야 하는 하나의 변경은 주된 목적에 맞는 scope를 선택하며, 단순히 파일이 여러 영역에 있다는 이유로 `repo`를 사용하지 않는다.

## 작업 방식

1. `git status --short`와 `git diff --stat`, `git diff --cached --stat`로 변경 범위와 기존 스테이징을 확인한다. 내용 diff는 아래 보안 점검의 민감정보 보호 절차에 따라 원문 비밀이 도구 결과에 노출되지 않게 확인한다. Git 저장소가 아니면 이를 알리고 메시지 초안까지 작성한다. 저장소 초기화는 요청받았을 때 진행한다.
2. `.vscode/settings.json`의 `conventionalCommits.scopes`를 읽고 변경의 주된 목적에 맞게 타입, scope, gitmoji를 선택한다. 메시지만 요청받으면 초안을 제공하고 커밋하지 않는다.
3. 스킬 단독 호출 또는 스테이징 커밋 요청이면 기존 인덱스를 커밋 대상으로 사용한다. 그 밖의 커밋 요청이면 요청 범위의 파일만 명시적으로 스테이징한다. 기존에 스테이징된 무관한 변경을 함께 커밋하거나 임의로 해제하지 않는다. 포함 범위가 불명확하면 확인한다. 독립적인 변경은 의미 단위로 나눈다.
4. [security-check 스킬](../security-check/SKILL.md)을 읽고 아래의 커밋 전 보안 점검을 먼저 수행한다. 이후 커밋 전 리뷰 기준에 따라 필요한 경우 [code-review 스킬](../code-review/SKILL.md)을 읽고 적용한다.
5. 커밋 전에 관련 검증을 실행한다. 기존 Node 개발 의존성을 사용하고, 설치가 필요하면 프로젝트 루트에서 `npm ci`를 실행한다. 메시지는 임시 UTF-8 파일에 작성하고 scope가 비어 있지 않고 설정의 허용 목록에 포함되는지 확인한 뒤 `npm run commitlint -- --edit <메시지 파일>`로 검사한다. 현재 `@commitlint/config-conventional`을 그대로 사용하며 scope 필수·허용 목록, gitmoji와 한글 규칙은 이 스킬을 통해 적용한다.
6. 검증한 메시지 파일로 `git commit -F <메시지 파일>`을 실행한다. Husky의 pre-commit은 lint-staged로 스테이징 파일에 Prettier를 적용하고 commit-msg는 commitlint를 실행한다. 훅이 실패하면 원인을 해결하고 변경 내용을 다시 확인한다. `--no-verify`로 우회하지 않는다.
7. 완료 후 커밋 해시, 메시지와 남은 변경 사항을 간단히 알린다. push와 기존 커밋 amend는 별도 요청이 있을 때만 수행한다.

## 커밋 전 보안 점검

- 커밋 생성 시 코드 리뷰보다 먼저 실행한다. 메시지 초안만 요청하면 자동 실행하지 않는다. 문서·포맷만 바뀌어도 비밀번호·API 키가 포함될 수 있으므로 민감정보 검사는 생략하지 않는다.
- 검사 범위는 스테이징된 변경과 새 파일의 인덱스 내용이다. 관련 코드는 영향 확인용으로 읽고, 미스테이징 변경·전체 저장소·Git 이력 검사로 자동 확장하지 않는다. 삭제된 줄에 포함된 비밀도 출력하지 않는다. 내용 확인은 security-check 스킬의 마스킹 원칙을 따르며, 검사 후에도 원문 비밀이 없다고 단정해 diff 전체를 출력하지 않는다.
- 코드·실행 설정 변경은 위험한 코드와 설정도 검사한다. 의존성·이미지·API 사용이 바뀌면 관련 버전의 취약점·deprecated 여부를 확인한다. 매 커밋마다 전체 의존성을 감사하지 않으며, 외부 조회나 감사가 불가능하면 미검증 범위와 이유를 알린다.
- 보안 문제가 없으면 결과와 한계를 간단히 알리고 코드 리뷰·검증을 계속한다. 발견 사항은 마스킹하여 보고하고 수정 여부를 확인한다. 수정하지 않기로 한 경우 남은 문제와 커밋 진행 의사를 확인하며, 명시적인 진행 지시가 있으면 재확인하지 않는다. 승인 전에는 수정하거나 커밋하지 않는다.
- 승인된 수정만 반영하고 관련 검증 후 해당 부분만 스테이징한다. 최종 스테이징 내용이 달라지면 변경된 부분과 영향에 대해 보안 점검을 다시 수행한다. 코드 리뷰 수정 또는 훅으로 내용이 바뀐 경우에도 적용하며, 이미 커밋된 뒤 문제가 확인되면 보고하고 amend는 별도 요청 없이 실행하지 않는다.
- 보안 점검 결과를 코드 리뷰에 전달하여 같은 문제를 중복 보고하지 않는다. 코드 리뷰에서도 민감한 값은 출력하지 않는다. 두 스킬의 수정 승인 원칙을 유지한다.

## 커밋 전 리뷰

- 커밋 생성 요청에 적용한다. 메시지 초안만 요청한 경우에는 리뷰를 자동으로 실행하지 않는다.
- `src/`, `web/`의 코드·프롬프트·동작에 영향을 주는 자산, Docker·실행 설정, 의존성 및 그 밖에 동작에 영향을 주는 설정 변경이 포함되면 code-review 스킬을 적용한다. 문서 또는 동작을 바꾸지 않는 포맷 변경만 있으면 생략하고 그 이유를 간단히 알린다. 파일 경로나 커밋 타입만으로 판단하지 않고 실제 diff를 확인한다.
- 리뷰 대상은 `git diff --cached`에 담긴 스테이징 변경이다. 부분 스테이징 파일은 인덱스의 내용(`git show :경로`)을 기준으로 검토한다. 관련 코드는 영향 확인용으로 읽되, 미스테이징 변경을 리뷰 대상에 포함하거나 자동으로 스테이징하지 않는다.
- 문제가 없으면 리뷰 결과를 간단히 알리고 검증·커밋을 계속한다. 동일한 스테이징 내용을 이미 리뷰했다면 결과를 재사용하고, 이후 변경된 부분과 그 영향만 추가 검토한다.
- 문제가 있으면 구체적인 발견 사항과 수정안을 보고하고 수정 여부를 확인한다. 승인 전에는 수정하거나 커밋하지 않는다. 수정하지 않기로 한 경우 남은 문제를 알리고 커밋 진행 의사를 확인한다. 사용자가 이미 해당 문제를 남긴 채 커밋하도록 명시했다면 다시 묻지 않는다.
- 승인된 수정 후 관련 검증을 실행하고, 승인 범위의 수정만 스테이징해 최종 diff와 리뷰 결과를 다시 확인한다. 부분 스테이징 파일은 기존 미스테이징 변경이 섞이지 않게 수정 부분만 반영한다. 리뷰 스킬에서 승인 없이 임의로 수정하지 않는 원칙을 유지한다.
